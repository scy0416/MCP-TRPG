# MCP-TRPG MVP 게임 규칙

## 1. 문서 목적

이 문서는 첫 번째 플레이 가능한 버전(MVP)의 게임 규칙과 AI GM, MCP 서버,
MCP App UI 사이의 책임을 고정한다. 구현 중 판단이 충돌하면 이 문서를 우선한다.

MVP의 목표는 복잡한 TRPG 규칙을 제공하는 것이 아니라 다음 게임 루프를 안정적으로
완성하는 것이다.

```text
장면 확인 → 자연어 행동 선언 → 필요 시 능력 판정 → 결과 기록 → AI 서술
```

## 2. MVP 범위

### 포함

- 싱글플레이 캠페인
- 캐릭터 한 명 생성
- 현재 장면 및 주변 대상 확인
- 자유 형식 행동 선언
- 네 가지 능력치를 사용하는 d20 판정
- NPC 및 사물과의 단순 상호작용
- 아이템 획득, 사용, 수량 변경
- HP 회복 및 피해
- 연결된 장면으로 이동
- 영속적인 현재 상태와 게임 이벤트 기록
- 사용자가 직접 조작하는 Dice UI

### 제외

- 멀티플레이
- 턴 순서와 initiative를 포함한 전투 시스템
- 직업, 레벨, 경험치, 성장
- 주문과 spell slot
- 장비에 의한 능력치 보정
- advantage/disadvantage 및 복합 주사위 규칙
- 치명타와 치명적 실패
- 월드맵 및 실시간 동기화
- 경쟁 플레이를 위한 부정행위 방지 RNG

제외된 기능은 MVP 규칙이나 데이터 구조에 암묵적으로 섞지 않는다.

## 3. 캐릭터 규칙

### 3.1 능력치

캐릭터는 다음 네 가지 능력치 modifier를 가진다.

| 능력치 | 용도 예시 |
|---|---|
| STR | 힘, 밀기, 부수기, 버티기 |
| DEX | 민첩, 균형, 은신, 정교한 조작 |
| INT | 지식, 조사, 추론, 마법적 이해 |
| CHA | 설득, 기만, 위압, 교섭 |

캐릭터 생성 시 `+3`, `+2`, `+1`, `+0`을 각 능력치에 한 번씩 배정한다.
MVP에서는 음수 modifier와 생성 후 능력치 변경을 지원하지 않는다.

### 3.2 HP

- 최대 HP는 `10 + STR modifier`다.
- 캐릭터는 최대 HP로 시작한다.
- 현재 HP는 항상 `0..max_hp` 범위여야 한다.
- 피해는 HP를 감소시키고 회복은 HP를 증가시키지만 최대 HP를 넘을 수 없다.
- HP가 0이 되면 캐릭터는 `incapacitated` 상태가 된다.
- `incapacitated`는 사망을 의미하지 않는다. AI GM은 구조, 후퇴, 포로가 됨 등
  이야기상 결과를 서술할 수 있지만 캐릭터를 영구 삭제할 수 없다.
- MVP에는 사망 판정과 부활 규칙이 없다.

## 4. 능력 판정

### 4.1 기본 공식

```text
total = d20 roll + ability modifier
success = total >= difficulty class (DC)
```

- d20 원값은 `1..20`의 정수다.
- 결과는 성공 또는 실패 중 하나다.
- 주사위 원값 1과 20에 별도 자동 실패/성공 규칙은 없다.
- 서버는 캐릭터의 현재 modifier와 저장된 DC를 사용해 결과를 계산한다.

### 4.2 난이도 기준

| DC | 난이도 | 의미 |
|---:|---|---|
| 5 | 매우 쉬움 | 위험이나 불확실성이 작음 |
| 10 | 쉬움 | 훈련 없이도 성공 가능 |
| 15 | 보통 | 실질적인 실패 가능성이 있음 |
| 20 | 어려움 | 뛰어난 능력이나 운이 필요 |
| 25 | 매우 어려움 | MVP 캐릭터에게 극히 어려움 |

AI GM은 원칙적으로 위 값을 사용한다. 중간값이 꼭 필요하면 `5..25` 범위의 정수를
사용할 수 있다. DC 5 미만인 행동은 판정 없이 성공시키고, DC 25를 넘을 행동은
현재 방법으로 불가능하다고 설명하거나 다른 접근을 제안한다.

### 4.3 판정이 필요한 경우

다음 조건을 모두 만족하면 판정을 만든다.

1. 결과가 불확실하다.
2. 실패가 현재 상황에 의미 있는 변화를 만든다.
3. 네 가지 능력치 중 하나로 해결할 수 있다.

다음에는 판정을 만들지 않는다.

- 일상적이고 위험이 없는 행동
- 이미 확정된 사실을 확인하는 행동
- 같은 목적과 접근으로 실패한 판정을 결과 변화 없이 즉시 반복하는 행동
- 서술만 필요한 대화나 감정 표현
- 현재 세계 상태상 명백히 불가능한 행동

### 4.4 판정 생명주기

1. AI GM이 능력치, DC, 이유를 정해 `create_check`를 호출한다.
2. 서버가 사용자, 캠페인, 캐릭터, 능력치와 현재 상태를 검증한다.
3. 서버가 modifier를 직접 조회하고 `pending` 판정을 저장한다.
4. Dice UI가 사용자에게 판정을 표시한다.
5. 사용자가 Roll을 눌러 생성된 d20 원값만 제출한다.
6. 서버가 저장된 판정을 기준으로 결과를 계산하고 한 번만 확정한다.
7. 서버가 판정 이벤트를 기록하고 AI GM이 확정 결과를 서술한다.

한 캠페인에는 동시에 하나의 `pending` 판정만 허용한다. 판정이 해결, 취소 또는
만료되기 전에는 새 판정을 만들 수 없다. 동일 판정의 재전송은 상태 변화를 두 번
일으키지 않아야 한다.

### 4.5 판정 결과와 상태 변경

`resolve_check`는 판정 결과와 이벤트를 확정하지만, 임의의 HP·아이템·장면 변경을
직접 받아 적용하지 않는다. 결과에 따른 상태 변화는 확정된 `check_id`를 근거로
서버가 검증 가능한 전용 게임 Tool을 통해 수행한다.

MVP의 첫 vertical slice에서는 `pending → resolved` 전환과 `ability_check` 이벤트
기록 자체가 영속 상태 변경의 완료 조건이다.

## 5. 아이템 규칙

- 아이템은 이름, 종류, 수량, 짧은 설명과 제한된 상태를 가진다.
- 같은 종류의 소모품은 수량으로 합칠 수 있다.
- 수량은 0 이상의 정수이며 0이 되면 인벤토리에서 제거할 수 있다.
- 아이템 획득과 사용은 서버 Tool을 통해서만 반영한다.
- 아이템 사용 효과는 서버가 허용한 효과만 적용한다.
- MVP 아이템은 능력치나 판정 modifier를 영구 또는 일시적으로 바꾸지 않는다.
- 존재하지 않거나 수량이 부족한 아이템은 사용할 수 없다.

## 6. 장면 규칙

- 캠페인은 정확히 하나의 현재 장면을 가진다.
- 장면에는 이름, 설명, 상태, 존재하는 NPC·적·사물과 이동 가능한 목적지가 있다.
- AI GM은 저장된 장면과 모순되는 대상을 임의로 존재한다고 확정하지 않는다.
- 이동은 현재 장면에 연결된 목적지로만 가능하다.
- 잠금이나 장애물이 있는 이동은 먼저 상호작용 또는 능력 판정으로 조건을 해소한다.
- 장면 이동은 서버 Tool이 성공한 뒤에만 서술상 확정된다.

## 7. 게임 이벤트 규칙

상태를 바꾸거나 판정을 확정한 서버 작업은 append-only 게임 이벤트를 남긴다.
최소 이벤트 종류는 다음과 같다.

- `campaign_created`
- `character_created`
- `ability_check_created`
- `ability_check_resolved`
- `interaction_completed`
- `item_acquired`
- `item_used`
- `hp_changed`
- `scene_changed`

이벤트 payload에는 재현과 설명에 필요한 ID, 이전 값, 이후 값, 판정 결과를
기록하되 access token이나 secret은 기록하지 않는다. 이벤트는 일반 게임 Tool로
수정하거나 삭제할 수 없다.

## 8. 권한과 책임

### 8.1 AI GM

AI GM은 다음을 담당한다.

- 사용자의 자연어 행동 의도 해석
- 저장된 게임 context에 기반한 장면과 결과 서술
- 판정 필요 여부, 사용할 능력치와 DC 결정
- 판정 성공 또는 실패에 어울리는 이야기 전개 제안
- 상태 변경이 필요할 때 적절한 MCP Tool 호출

AI GM은 다음을 해서는 안 된다.

- 주사위 결과를 직접 생성하거나 사용자를 대신해 굴리기
- Roll 전에 성공 또는 실패를 확정하기
- 서버 응답과 다른 판정 결과를 서술하기
- Tool 호출 없이 HP, 아이템, 위치 등 영속 상태를 변경했다고 선언하기
- DB row나 내부 인증 구조를 사용자에게 요구하기
- 저장된 세계 상태와 모순되는 사실을 임의로 확정하기

### 8.2 MCP 서버

MCP 서버는 게임 상태의 유일한 쓰기 관문이며 다음을 담당한다.

- access token 검증과 사용자 식별
- 캠페인 접근 권한 및 리소스 소유 관계 확인
- Tool 입력, 현재 상태 및 허용된 상태 전이 검증
- 능력치 modifier 조회와 판정 결과 계산
- 판정의 중복 해결 방지 및 idempotency 보장
- 트랜잭션 단위의 상태 변경과 이벤트 기록
- AI에 필요한 최소 목적별 context 제공

서버는 다음을 해서는 안 된다.

- 프로세스 메모리를 게임 상태의 authoritative source로 사용하기
- AI나 UI가 보낸 modifier, DC 재전송값, success 값을 신뢰하기
- 사용자 요청을 일상적으로 service-role 권한으로 우회하기
- 이야기 문장이나 창작적 결과를 임의 생성하기

### 8.3 Dice MCP App UI

Dice UI는 다음만 담당한다.

- 서버가 확정한 판정 이유, 주사위, modifier와 DC 표시
- 명시적인 사용자 Roll 입력 수신
- Web Crypto 기반 주사위 원값 생성
- `check_id`와 `rolls`만 `resolve_check`에 제출
- 서버가 반환한 확정 결과 표시

Dice UI는 다음을 해서는 안 된다.

- modifier, DC, total, success 또는 게임 효과를 결정해 제출하기
- Roll 버튼을 누르기 전에 자동으로 굴리기
- service-role credential 또는 서버 secret을 보유하기
- 서버 응답 없이 영속 상태가 바뀌었다고 표시하기

## 9. Authoritative source

Supabase PostgreSQL이 캠페인, 캐릭터, 장면, 아이템, pending 판정과 이벤트의
authoritative source다. AI 대화 기록, MCP 서버 메모리, Dice UI 로컬 상태는 게임
상태의 근거가 아니다.

따라서 서버 재시작, Cloud Run 인스턴스 교체, 브라우저 새로고침 또는 대화 재개
후에도 Supabase에서 읽은 상태만으로 게임을 계속할 수 있어야 한다.

## 10. MVP 플레이 예시

```text
사용자: 잠긴 철문을 발로 부순다.

AI GM: 의미 있는 실패 가능성이 있으므로 STR, DC 15 판정을 요청한다.

서버: 캐릭터의 STR +3을 조회하고 pending 판정을 저장한다.

Dice UI: 사용자가 Roll을 누른 뒤 d20 원값 16을 제출한다.

서버: 16 + 3 = 19, 19 >= 15이므로 성공으로 한 번만 확정하고 이벤트를 기록한다.

AI GM: 확정된 성공 결과를 바탕으로 문이 부서지는 상황을 서술한다.
```

## 11. Stage 0 완료 기준

- 포함 기능과 제외 기능이 구분되어 있다.
- 기본 능력치, 판정, HP, 아이템과 장면 규칙이 정의되어 있다.
- AI GM, MCP 서버와 Dice UI의 책임과 금지 사항이 구분되어 있다.
- 영속 상태의 authoritative source가 명시되어 있다.
- 첫 vertical slice에서 어떤 상태 변경까지 검증할지 명시되어 있다.
